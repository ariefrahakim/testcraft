Runbook · v1.0

Autonomous spec-driven Playwright QA, one slash command.

qa-agent ships as a Claude Code plugin from Hubexo's marketplace. It pulls test scenarios written by the user-acceptance agent, generates Playwright code against your live frontend, runs it on Chromium, uploads to Qase, self-heals broken selectors, routes defects onto Jira or Azure Boards, and opens the PR — all from one command.

Node ≥ 20 Playwright Qase (TMS) Jira · Azure Boards TDD · BDD · both Chromium only

0 Where scenarios come from#

qa-agent does not invent tests. It consumes them:

upstream user-acceptance agent → source of truth Qase plan → this plugin qa-agent → artifact Playwright + PR

A separate agent (user-acceptance / requirements agent) authors user stories and produces Qase test cases — the plan id, the scenarios (Gherkin for BDD, classic action/expected for TDD), the "To be automated" flag. That plan is the input qa-agent reads. The plugin never edits the plan back; it treats Qase as read-only source of truth.

The tracker (Jira or Azure Boards) hosts the delivery envelope: an Epic / PBI / User-Story with four subordinate tickets — [TM-…] (manual test-case ticket, names the plan), [TA-…] (automation ticket, the trigger home), [FE-…] and [BE-…] (defect-routing targets). The plugin reads the parent, resolves those children, and runs the pipeline against the plan the [TM-…] points at.

2 Scaffold your QA repo#

In an empty directory that will become your QA repo:

mkdir qa-playwright-<app-slug> && cd qa-playwright-<app-slug>
# Open Claude Code here, then:
/qa-agent:setup

Setup is interactive. It asks two shape questions first, then app-specific values:

Stack — jira or azure

jira GitHub Actions

Test management: Qase. Tracker: Jira. Hierarchy is Epic → Story → [TM]/[TA]/[FE]/[BE]. Comments use ADF. CI ships as .github/workflows/regression.yml. Run logs sync to Confluence via hubexo-spec-sprint.

azure Azure Pipelines

Test management: Qase (same as jira). Tracker: Azure Boards. Hierarchy is Product Backlog Item (PBI) → Task — or Epic → Task flat variant — with the same [TM]/[TA]/[FE]/[BE] prefixes on Task work items. Comments use HTML. CI ships as azure-pipelines.yml. Run logs sync to Azure DevOps Wiki via the plugin-owned utils/run-log-to-azure-wiki.ts.

Style — tdd, bdd, or both

tdd steps_type: classic

Qase cases carry action/expected rows. qa-codegen emits one tests/e2e/<area>/<module>.spec.ts per module, one test() per case, one test.step() per row.

Layers: Spec → Step → Page → Locator.

bdd steps_type: gherkin

Qase cases carry Given/When/Then. qa-codegen mirrors them into features/<area>/<module>.feature + steps/<area>/<module>.steps.ts. playwright-bdd compiles them to .features-gen/ at run time.

Layers: Feature → Step → Page → Locator.

Pick both if the same Qase project mixes classic + Gherkin cases; each case's steps_type decides which branch runs.

App values

APP_NAME, BASE_URLHuman-readable name + the app-under-test URL.
POST_LOGIN_URL_PATTERNRegex the URL must match after login (e.g. /dashboard).
TMS_PROJECTQase project code (e.g. ONEBID) — same on both stacks.
FE_REPO_URL, FE_BRANCHFrontend source repo (SSH URL, or Azure Repos HTTPS URL on --stack azure).
TRACKER_BASE_URL / AZURE_ORG_URLJira tenant URL, or Azure DevOps org URL.
TRACKER_PARENT_IDDefault defect parent — Jira epic/story key, or Azure work-item id.

The scaffold produces a repo that typechecks + lints clean out of the box. Then fill .env:

cp .env.example .env
# Fill in USER_ID, USER_PWD, API_TOKEN (Qase), tracker token / PAT, SSH_KEY (or Azure PAT for FE),
# plus AZURE_WIKI_AGENT_LOGGER when --stack azure and you want run logs on Azure Wiki.
npm install && npm run install:browsers
npm run fe:sync
npm run typecheck && npm run lint

3 Trigger the pipeline#

One command does the whole pipeline end-to-end. Pick the input that matches the artifact you have:

You haveCommand
A Jira epic / story / [TA] key with a [TM-…] child that names a plan /qa-agent:qa-agent NLM-4
An Azure Boards Epic / PBI / [TA-…] Task id /qa-agent:qa-agent AB#12345
Only a Qase plan id (no tracker ticket) /qa-agent:tms plan:8
Only a single case id /qa-agent:tms TC-2045

What the orchestrator runs

1 read tracker → 2 qa-codegen generate → 3 qa-runner run + Qase upload → 4 qa-healer heal ≤2 retries → 5 qa-defect comment + transition → 6 summary → 7 qa-pr commit + open PR
Fully autonomous. The orchestrator never asks the user a question mid-flow. It resolves ambiguity with sensible defaults (chromium headless, first [TM] child wins, one heal cycle per affected module) and only stops on documented conditions — the parent has no [TM-…] child, the plan source names no plan, or Qase / tracker credentials are missing.

Sub-commands — same pipeline, one step at a time

IntentCommand
Just generate — no run/qa-agent:qa-agent-generate plan:<id>
Just run — fresh Qase cycle/qa-agent:qa-agent-run plan:<id> | <module> | TC-xxxx [--headed]
Fix broken selectors (3 attempts)/qa-agent:qa-agent-heal <module> | TC-xxxx
Route last run's failures to tracker children/qa-agent:qa-agent-defect <EPIC-KEY | AB#id>
Open / update PR for current branch/qa-agent:qa-agent-pr
Refresh framework files after a plugin update/qa-agent:upgrade

Given a Jira user story NLM-355 with subtasks [TM-01] NLM-511 (Qase plan 8), [TA-01] NLM-512, [FE-01] NLM-510, [BE-01] NLM-509:

/qa-agent:qa-agent NLM-355

Step 3 — qa-runner: chromium headless, 9/9 passed (2m 14s), Qase run 128 uploaded
Step 4 — qa-healer: skipped (all green)
Step 5 — qa-defect: summary comment on [TM-01] NLM-511 + [TA-01] NLM-512; both → Waiting to Deploy
Step 7 — qa-pr: PR #41 opened against master

4 Stacks covered#

Two stacks are supported today. Everything above utils/tms.ts (Qase gateway) and utils/tracker.ts (tracker gateway) is stack-agnostic — the same generated code runs on both, only the two gateway files differ.

Never mixed. A repo is either jira or azure — swapping stacks in place is not supported. Scaffold a new repo with the other stack and move pages/, locators/, tests/, features/, steps/, and fixtures/ across; they are stack-agnostic by design.

6 Under the hood — five agents#

  1. qa-codegen — generate

    Syncs the FE repo, pulls the Qase plan, mines data-testid from FE source, reuses existing pages/locators before creating new ones. Emits .spec.ts for classic or .feature + .steps.ts for Gherkin. Runs typecheck + lint. Self-verifies each happy path live via the Playwright MCP before handing off, so a later runner red is a real regression.

  2. qa-runner — execute + Qase upload

    Mints a fresh Qase cycle from the plan, runs Chromium (headless by default; --headed for demos), uploads status + video + screenshot + trace per case. Reads QASE_MODE + API_TOKEN to decide upload vs. local-report-only.

  3. qa-healer — self-heal (3 attempts max)

    On a red case, re-resolves the failing selector through the source-of-truth chain: existing locator → existing page → FE source → real DOM. Re-runs after each attempt, capped at fix + 2 retries. Never downgrades priority (testid → xpath is banned). If still red after 3 attempts, escalates to qa-defect — the failure is a product bug, not a selector artifact.

  4. qa-defect — route + comment + transition

    Classifies each failure as FE-sourced or BE-sourced (error signature + trace network log; BE wins on disagreement). Uploads the screenshot to the matching [FE-…] or [BE-…] child, comments the QA bug-report template with the screenshot embedded inline, transitions to TEST: FAILED/BUGS. Always posts a per-run summary on [TM-…] + [TA-…]. On an all-green run: transitions both to Waiting to Deploy. Never creates a bug ticket — comment + transition + attachment only.

  5. qa-pr — commit + open PR

    Stages the generated + healed files by explicit path (never git add -A), commits on the current feature branch, pushes, and calls gh pr create/edit with the tracker context stamped into the body — Story / [TM] / [TA] / [FE-*] / [BE-*] tickets, Qase run URL + counts, deep-links to per-failure comments, generated-vs-reused asset list. Never force-pushes, never bypasses hooks.

An orchestrator above these five drives the whole pipeline. After every step it fires two calls:

  1. hubexo-spec-sprint:run-logger (prefilled) — writes a row to logs/run-log.jsonl with token_cost, duration, manual_effort, notes, and the per-step agent name. Identical on both stacks. Never bypass this call by echo >> jsonl — the token/duration numbers cannot be recovered later. The Azure Wiki syncer scans for missing duration/token_cost before writing and prints a WARN per incomplete row; set RUN_LOG_STRICT=1 to make it abort instead of pushing partial data.
  2. Sync — the only step that differs by stack:
    • jira: hubexo-spec-sprint:run-logger-sync → Confluence (one page per agent).
    • azure: npm run run-log:sync (utils/run-log-to-azure-wiki.ts) → Azure Wiki (one child page per agent under the parent named by AZURE_WIKI_AGENT_LOGGER).

7 Common issues#

fe:sync fails with 403 or "Repository not found"

Two typical causes:

  • SSH URL, wrong key. Point SSH_KEY at the private key that has org access (absolute path — ~ is not expanded).
  • Azure Repos HTTPS, wrong scope. Ensure AZURE_PAT includes Code (Read). fe-repo-sync uses http.extraheader, so the PAT never lands in git config.

transitionToWaitingToDeploy returns 400 on Azure

Fixed in the current release. If you're upgrading from an older scaffold, run /qa-agent:upgrade — the fix is in utils/azure-client.ts.

Wiki sync 405 Method Not Allowed

AZURE_PAT is missing Wiki (Read & Write). Edit the PAT in Azure DevOps → user settings → Personal access tokens → check the Wiki scope.

Orchestrator aborts at Step 1 — "no [TM-…] child"

The parent (Epic / Story / PBI) has no ticket with a [TM-…] summary prefix. Either create one whose description names the Qase plan (e.g. plan:8), or bypass the tracker and drive from Qase directly: /qa-agent:tms plan:8.

Playwright says bidSearchPage is unknown parameter

New page object not wired into shared/pom-fixtures.ts. Add it to the Pages interface and to the pomFixtures object — the plugin scaffold ships only loginPage; every subsequent module needs one line in each place.
